- `connectome service install <recipe>` writes this install's service and starts it, then checks it. On Linux it writes a systemd user unit, `~/.config/systemd/user/connectome-<name>.service`, and on macOS a launch agent, `~/Library/LaunchAgents/com.animalabs.connectome.<name>.plist`, each named after the install's working directory, the directory that holds `.env` and `data/`. The service runs the install's `start.js` with the recipe and `--headless` in that directory, with an explicit PATH and, as `DATA_DIR`, the data directory `install.json` names. A launch agent runs while its user is logged in.
  - The unit sets `CONNECTOME_SUPERVISED=1` only once systemd shows that it restarts the host when it exits with 75, as an update's restart does, and with 1, as a failed update does. A launch agent always sets it, since the `KeepAlive` it writes restarts the host whenever it exits other than with 0.
  - When `term-sessions-mcp` is installed beside the host, for the resident's shell, its daemon gets a unit too. Its port and token are `SESSION_SERVER_PORT` and `SESSION_SERVER_TOKEN` in `.env`. Where they aren't there, it picks a port from 3100 that is free when picked and makes a token, writes them there, and names the port. The daemon listens on localhost only. The daemon gets them in its own unit, readable by its user alone, never on its command line, and never the rest of `.env`. A `.env` that holds the token and is open to others than its user is made readable by its user alone, and the command says so.
  - Then it waits up to a minute for the host to answer, and checks that each unit is running and shows the host's log, with the install's secrets replaced by their names. For a host that's running on Linux, it shows the first 40 lines and every later line that reads as an error, and marks and counts each such line without failing on it, since a working install's servers can write such lines; a check that passes with a marked line ends by saying to put it right if it's a problem, then run the command again, which restarts the host. A start that ended is shown by its last 40 lines, with nothing marked, since a word match there can mark a line beside the cause. On Linux the wait ends early once systemd has stopped or restarted the host, it says how often systemd has restarted each unit, it checks that the host's unit restarts it on 75 and 1 and sets the line, and the log is the journal's lines from the host's own process in the first minute of its latest start, or for a host that isn't active, that start's last lines. For a host running again after systemd restarted it, it also shows the journal's last lines about the start that ended before that one, such as how its process exited, where the unit's last 200 journal entries hold them, and says so where they can't tell which start that was. On macOS the log is its file since the command last loaded the agent, which keeps the one before as `agent.log.previous`; it can hold more than one start of the host, so it's shown by its last 40 lines with nothing marked. When a check fails, it exits 1 and says what to do next. If the run changed the recipe, it also gives the recipe recorded before, with the install's secrets replaced by their names, and, when that recipe holds none of them, the line that puts it back if the host's recipe loader still takes it; when the secrets can't all be kept out, it says only that another recipe was recorded.
  - Every run restarts each unit it writes, which starts one that isn't running, so the service runs the recipe and `.env` as they are now. A re-run therefore restarts a resident that's running, and on Linux its shell daemon's terminal sessions end with it. On Linux it enables the units, which start at boot, and says so, and it clears systemd's start-limit count for them first, since the run is the request to start them. Run again, it keeps the recorded recipe. Once `term-sessions-mcp` is gone, it stops and removes the shell daemon's unit. It leaves alone one of that name that runs another install, and one still running with its file gone that systemd no longer holds, which nothing then places in an install, naming the line that stops it.
  - It refuses, writing nothing, when the host's own recipe loader, run in the working directory with `.env` and the variables its unit and launcher set, refuses the recipe, giving its words unless the install's secrets can't all be kept out of them, so a running service stays as it was; when it runs inside the service it would restart, saying to run it from a terminal outside it; when linger is off for the user, printing the root line that turns it on; when `.env` is a link, or has a line outside the form setup reads and writes it in, as setup refuses it; when a unit of either name runs another install, as its file says or as systemd has it loaded, or still runs with its file gone once systemd no longer holds it; and, on Linux, when systemd holds another unit with that directory as its own, running or not, naming its kind and file and the line that shows its state and process.
  - It records the service in the install's `service.json` once it has written a unit file, also when it stops partway, and `connectome` alone then shows how to follow the host's log, and that `connectome service stop` and `connectome service start` stop and start it, also when its host can't be reached. With it recorded, `connectome`, `connectome send` and `connectome update`, but for its `back` words, say to start a host that isn't running with `connectome service start`. A `service.json` it can't read makes `connectome` alone exit 1, naming the file.
- `connectome service stop` stops the service `connectome service install` recorded, its host and shell daemon, saying which were running, and exits 1 when it can't stop one. It doesn't disable or remove the service, and says whether it starts again by itself: at boot on Linux, while its unit is enabled and linger is on, and at the user's next login on macOS. Once its units have stopped, it reads the update journal and mark as the next start's launcher reads them, and says what that start does about an update: it falls back from a trial that hadn't committed, goes on with a Go back that was cut off, or takes up a marked switch or Go back.
  - `connectome service start` says the same about an update before it starts the host, once a unit on its way down has stopped: it runs `systemctl --user stop` for one, which waits for that. It clears systemd's start-limit count for the units that aren't running, one between restarts among them, and starts them, or on macOS loads each launch agent that isn't loaded, setting its log aside first as install does, and starts one that's loaded but not running. It leaves a running unit as it is. Then it waits for the host and checks the service as install does, and exits 1 when it can't start a unit, or the host doesn't answer, or the check fails. It refuses when a unit file the record names is gone.
  - Both refuse with no service recorded, or with a `service.json` they can't read; when a unit it names now runs another directory, by its file or as systemd has it loaded, or still runs with its file gone once systemd no longer holds it, or on macOS is still loaded with its file gone, as install refuses it, so they leave another install's service alone; and when run from inside the service, as install does, saying to run them from a terminal outside it.
